# صندوق المشروع — تطبيق إدارة ممولين ومصروفات (PWA أوفلاين)

تطبيق محلي (Progressive Web App) لإدارة صندوق مشروع واحد: تسجيل الممولين ونسب تحمل كل واحد منهم للمصروفات، إنشاء بنود مصروفات، تسجيل المصروفات والمساهمات، ومتابعة رصيد الصندوق — كل ده من غير سيرفر أو إنترنت. البيانات مخزّنة بالكامل على جهازك (IndexedDB)، والتطبيق قابل للتثبيت على الشاشة الرئيسية في الموبايل أو الكمبيوتر، ويشتغل بدون نت تمامًا بعد أول فتحة.

## المميزات

- **الممولون**: إضافة أي عدد من الممولين، مع نسب تحمل مصروفات تتساوى تلقائيًا، وإمكانية تحديد نسب مخصصة (يجب أن يساوي المجموع 100%).
- **الخزنة**: رصيد واحد مُشتق دايمًا من دفتر الحركات (مش رقم بيتعدل يدويًا) = إجمالي المساهمات − إجمالي المصروفات.
- **بنود المصروفات**: إنشاء بنود حرة (بناء، كهرباء، سيراميك...) مع ميزانية تقديرية اختيارية ومتابعة نسبة الاستهلاك.
- **تسجيل مصروف**: يمنع الصرف لو تجاوز الرصيد المتاح (إلا لو فعّلت "السماح بالسحب على المكشوف" من الإعدادات)، ويوزّع المصروف على الممولين حسب نسبهم تلقائيًا مع توزيع فروق التقريب بشكل حتمي (المجموع دايمًا بيطابق قيمة المصروف بالظبط).
- **تقسيم مصروف على أكتر من بند**: مبلغ واحد يتوزع على عدة بنود دفعة واحدة، وكل بند بيتسجل كحركة مستقلة.
- **مستحقات الموردين**: فاتورة معروف إجماليها ومدفوع منها جزء — الباقي بيتسجل كمستحق للمورد ويتسدد على دفعات. إلغاء مصروف الفاتورة نفسه بيلغي المستحق معاه (ودفعات السداد اللي اتدفعت عليه لازم تتلغي الأول)، وكذلك الصنف اللي كل دفعاته اتلغت مبيفضلش عليه باقي للمورد.
- **أصناف تتوزع لاحقًا**: صنف هيتستخدم في أكتر من بند (4 نقلات رمل مثلاً) أو دفعة مقدمة لسه مش معروف بندها. بيتسجل باللي اتدفع فعلاً (حتى لو عربون)، وإجمالي الحساب اختياري: لو معروف بيظهر الباقي للمورد على كارت الصنف وفي «المستحقات للموردين»، ولو مش معروف يتساب فاضي ويتحدد بعدين. تتضاف عليه دفعات بعدين، ويتوزع على البنود **بعدد الوحدات** أو **بالنسبة المئوية** أو **بمبلغ ثابت**. نصيب كل بند في التوزيع بالوحدات/النسبة مش رقم مخزّن: بيتحسب من المدفوع للصنف لحد دلوقتي، فلو اتدفع باقي الحساب أو اتلغت دفعة بيتعدل لوحده.
- **إلغاء حركة**: أي حركة (مساهمة أو مصروف) ممكن تتلغي بحركة عكسية موثقة بسبب، من غير حذف الحركة الأصلية نهائيًا.
- **تعديل من غير حذف**: بيانات أي حركة اللي مفيهاش فلوس (الوصف، التاريخ، المورد، طريقة الدفع، رقم الفاتورة) بتتعدل مباشرة من كشف البند أو كشف الممول، وكذلك اسم الصنف وكميته ووحدته، واسم مورد المستحق وإجمالي فاتورته، وإلغاء أرشفة البند. المبلغ والبند والممول مبيتعدلوش في مكانهم: بيتغيروا بس بإلغاء الحركة وتسجيلها من جديد، عشان كل رقم في الدفتر يفضل له أصل.
- **كشوف حساب**: كشف حساب كامل لكل ممول (مساهمته الفعلية مقابل نصيبه من المصروفات) ولكل بند مصروفات.
- **تقارير نضيفة**: التقارير (والـExcel والـPDF المتصدَّر منها) بتعرض اللي ساري بس. الحركات الملغاة وحركات إلغائها، والفواتير والأصناف الملغاة، وعلامة «بياناتها اتعدّلت» مخفيين افتراضيًا ومحفوظين في البيانات، وبيظهروا بخيار «إظهار الملغي وعلامة التعديل». الإجماليات واحدة في الحالتين لأن الحركة الملغاة وحركة إلغائها مجموعهم صفر. التقرير الشامل بيكتب بند كل مصروف واسم ممول كل مساهمة.
- **تصدير Excel وPDF**: لكل بند، لكل ممول، أو تقرير شامل للمشروع.
- **نسخ احتياطي**: تصدير/استيراد ملف JSON يدويًا، بالإضافة لنسخة تلقائية يومية محفوظة على الجهاز (آخر 14 نسخة).
- **PWA أوفلاين بالكامل**: بعد أول فتحة، التطبيق والبيانات شغالين بدون أي اتصال إنترنت.

## لماذا البنية دي بالذات

المشروع ده مخصص **لمستخدم واحد** يشتغل بيه على موبايله **من غير سيرفر ومن غير إنترنت**. علشان كده مفيش Backend ولا قاعدة بيانات مستضافة (NestJS/PostgreSQL كانت الخطوة الأولى الغلط قبل ما يتوضح المطلوب الفعلي). البيانات بتتخزن محليًا في المتصفح نفسه (IndexedDB عبر مكتبة Dexie)، والتطبيق بيتحمّل مرة واحدة ويشتغل بعدها Offline بالكامل بفضل Service Worker.

**تحذير مهم**: البيانات موجودة على الجهاز بس. لو الموبايل ضاع أو اتعمله Reset، البيانات بتضيع إلا لو عملت نسخة احتياطية (من شاشة "المزيد") وحفظتها في مكان تاني (Google Drive، بريد إلكتروني... إلخ).

## التقنيات

- **Vite + React + TypeScript** — واجهة التطبيق
- **Tailwind CSS v4** — التنسيق، بدعم RTL كامل
- **Dexie.js (IndexedDB)** — تخزين البيانات محليًا على الجهاز
- **vite-plugin-pwa** — تحويل التطبيق لـ PWA قابل للتثبيت والعمل Offline
- **SheetJS (xlsx)** — تصدير تقارير Excel
- **jsPDF + html2canvas-pro** — تصدير تقارير PDF بدعم كامل للعربي (عن طريق تصوير العرض الفعلي بدل رسم النص، لتفادي مشاكل تشكيل الحروف العربية في مكتبات PDF العادية)

كل الحسابات المالية بتتم بوحدة **القرش الصحيح** (عدد صحيح = 1/100 جنيه) بدل الأرقام العشرية (float)، لمنع أي خطأ تقريب في الحسابات.

## التشغيل محليًا

```bash
pnpm install
pnpm run dev
```

التطبيق هيفتح على `http://localhost:5173`.

## البناء للإنتاج

```bash
pnpm run build
pnpm run preview   # لتجربة نسخة الإنتاج محليًا
```

مخرجات البناء في مجلد `dist/` — دول الملفات اللي بتتنشر (مثلاً على GitHub Pages أو أي استضافة Static ثابتة). مفيش سيرفر أو قاعدة بيانات مطلوبة للنشر؛ أي استضافة ملفات ثابتة كافية.

## هيكل المشروع

```
src/
  domain/      منطق الأعمال: الأرقام المالية (money.ts)، محرك الدفتر المالي (ledger.ts)
  db/          تعريف قاعدة بيانات IndexedDB (Dexie)
  backup/      النسخ الاحتياطي والاستعادة
  export/      تصدير Excel وPDF
  pages/       شاشات التطبيق
  components/  عناصر واجهة مشتركة
```

## ملاحظات على دقة الحسابات

- رصيد الخزنة **مش رقم مخزّن** — بيتحسب دايمًا من مجموع كل الحركات في دفتر الحركات (`ledger.ts` → `getVaultBalanceQirsh`).
- أي إلغاء لحركة بيتم عن طريق إنشاء حركة عكسية جديدة مرتبطة بالأصلية، مش حذف. الحركة الأصلية بتفضل موجودة ومُعلَّمة "ملغاة".
- مصروف أي بند = حركاته المباشرة + نصيبه من الأصناف الموزَّعة بالوحدات/النسبة (`ledger.ts` → `getSpentByCategory`، مصدر واحد لكل الشاشات). فلوس الصنف نفسها بتتخصم من الخزنة مرة واحدة بس وقت الدفع؛ التوزيع على البنود مش بيخصم تاني.
- توزيع المصروف على الممولين بيستخدم خوارزمية "أكبر باقي" (largest remainder method) لضمان إن مجموع الأنصبة يطابق قيمة المصروف بالظبط مهما كانت النسب.
